## Find a release

Published versions and release notes are listed on [GitHub Releases](https://github.com/ZihxS/RespKit/releases). The [changelog](https://github.com/ZihxS/RespKit/blob/main/CHANGELOG.md) summarizes changes to the library.

Install the latest released core package from an existing Go module:

```bash
go get github.com/ZihxS/RespKit/resp
```

To install a specific release, append its tag to the package path with `@`. Check the selected version's module manifest for its Go requirements.

Optional integrations are separate Go modules with their own dependencies and Go requirements. A root release tag does not version a nested module; nested modules require tags that include their directory path.

If an adapter uses a new core API, such as the `resp.Code...` constants, publish the core release first and update the adapter's required core version before tagging the nested module. Verify installation without the repository's local `replace` directive so the released dependency graph includes every API the adapter uses.

## Requirements before publication

Submit release changes through a pull request and satisfy every check required by the main branch. The branch must be up to date before merging, and the same requirements apply to maintainers.

Quality gates run only on manual dispatch. Select `full` in **Actions → RespKit quality gates → Run workflow**, or use `gh workflow run ci.yml --ref your-branch -f suite=full`. The default `core` suite intentionally skips platform and integration checks and does not satisfy the merge or release requirements.

Branch protection can enforce these requirements, but publication does not require changing repository settings. When `main` is unprotected, the maintainer must manually confirm that every job in a `full` quality-gates run passed for the latest pull-request commit before merging, then manually dispatch `full` on `main` and verify a successful run for the exact commit before creating release tags. Confirm each run's commit SHA. Pending, failed, canceled, or skipped quality-gates jobs do not satisfy the release checks.

The release checks cover:

| Area | What to verify |
| --- | --- |
| Public API | Existing helpers work without configuration, and application data keys remain unchanged |
| Error safety | Raw internal errors stay hidden by default, and public codes and statuses remain stable |
| Core checks | Tests, go vet, race detection, and the combined statement-coverage requirement pass |
| Platform support | Core tests execute on the platforms configured in CI |
| HTTP frameworks | Runtime tests pass against the upstream versions selected by the integration suite |
| Optional integrations | Mapper tests pass in their separate modules |
| Documentation | Examples, internal links, changelog entries, and the static site build are current |
| Repository security | Private reporting and Dependabot alerts are enabled; review main branch protections and manually verify all quality gates when protection is not enabled |

Use the [CI workflow](https://github.com/ZihxS/RespKit/blob/main/.github/workflows/ci.yml) and [GitHub Actions](https://github.com/ZihxS/RespKit/actions/workflows/ci.yml) to inspect the current checks and their results. The [compatibility guide](/verification) explains the scope of those results.

Review open Dependabot alerts before publication and resolve or document any that affect the release. Report suspected vulnerabilities through the private channel described in the [security guide](/security).

## Publish a release

1. Update the changelog and relevant documentation. Preserve the public API or describe breaking changes clearly.
2. Run the checks in the [testing guide](/testing). Keep raw internal errors hidden and preserve the zero-configuration response helpers.
3. Submit changes through a pull request, manually dispatch `full` for its latest reviewed commit, and merge only after every required check passes.
4. Manually dispatch `full` on `main` and confirm the exact commit to release has a successful run with every job passed. Review open Dependabot alerts and resolve or document any that affect the release.
5. Confirm private reporting and Dependabot alerts remain enabled. Review main branch protections; when `main` is unprotected, manually verify every quality-gates job for the latest pull-request commit and the exact `main` commit as described above.
6. Create the version tag and GitHub release from that verified commit. Include installation instructions, changes, compatibility information, and links to verification results.
7. Verify the published tag resolves to the intended commit, then update the release links in the documentation and manually dispatch `pages.yml` on `main` to publish them.

Keep published version tags unchanged. Publish a new version when a released package needs a correction.
