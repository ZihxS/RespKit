## Current release

[RespKit v1.0.0](https://github.com/ZihxS/RespKit/releases/tag/v1.0.0) is published from commit `cae6b7684834cf09aebf8a5786f056e89c58e399`. All six jobs in its [quality-gates run](https://github.com/ZihxS/RespKit/actions/runs/38072670243) passed before publication.

Install the released core package from an existing Go module:

```bash
go get github.com/ZihxS/RespKit/resp@v1.0.0
```

The root module supports Go 1.22 and later. Optional integrations are separate Go modules with their own dependency and Go requirements. A root release tag does not version a nested module; nested modules require tags that include their directory path.

## Repository protections

Private Vulnerability Reporting and Dependabot alerts are enabled. Report suspected vulnerabilities through the [private reporting form](https://github.com/ZihxS/RespKit/security/advisories/new) or the contact listed in the [security guide](/security).

The main branch requires pull requests and the following GitHub Actions checks:

| Required check | What it verifies |
| --- | --- |
| Core / Go 1.27.x / ubuntu-latest | Core tests and go vet on Linux |
| Core / Go 1.27.x / macos-latest | Core tests and go vet on macOS |
| Core / Go 1.27.x / windows-latest | Core tests and go vet on Windows |
| Core race and coverage | Race detection and 100% combined statement coverage for resp and internal runtime packages |
| Upstream framework runtime tests | Race-enabled tests against the pinned upstream routers |
| Optional pgx mapper tests | Race-enabled tests for PostgreSQL error mapping |

Branches must be up to date with main before merging. These requirements also apply to administrators. Force pushes and deletion of main are disabled.

A passing CI run verifies the versions listed in the [verification report](/verification). Dependabot alerts remain a separate review responsibility; a successful test run does not establish that dependencies have no known vulnerabilities.

## Publish a future release

1. Update the changelog and relevant documentation. Preserve the public API or describe breaking changes clearly.
2. Run the checks in the [testing guide](/testing). Keep raw internal errors hidden and preserve the zero-configuration response helpers.
3. Submit changes through a pull request and merge only after every required check passes.
4. Confirm the exact main commit to release has a successful quality-gates run. Review open Dependabot alerts and resolve or document any that affect the release.
5. Confirm private reporting, Dependabot alerts, and main branch protection remain enabled.
6. Create the version tag and GitHub release from that verified commit. Include installation instructions, changes, compatibility information, and links to verification results.
7. Verify the published tag resolves to the intended commit, then update the release links in the documentation.

Keep published version tags unchanged. Publish a new version when a released package needs a correction.
